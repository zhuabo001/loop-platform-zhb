# 什么是 Standard 审查

Standard 审查检查的不是“功能能不能跑”，而是“实现方式是否符合项目约定，代码是否容易长期维护”。

## 它依据什么

主要依据项目自己的规则：

- `AGENTS.md` 中的仓库工作规约；
- 适用且仍有效的 ADR，例如 Phase 4 主要参考 ADR-009；
- `package.json`、TypeScript、测试和数据库检查等工具配置；
- roadmap、Issue 流程等阶段和协作约定。

通用的代码异味（如重复代码、职责混杂、命名不清）只能作为改进建议，不能当作项目硬性规定。项目明确写下的规则优先于这些通用建议。

## 它和另外两种审查有什么不同

| 审查 | 要回答的问题 |
| --- | --- |
| Standard | 是否按项目约定的方式实现？ |
| Spec | 是否完整、正确地实现了需求？ |
| 对抗性 | 遇到恶意输入、并发和异常情况时会不会出问题？ |

例如，同一段文件读取代码可能同时出现两类问题：绕过项目规定的公共接口，这是 Standard 问题；通过符号链接替换读取到越界文件，这是对抗性问题。它们关注的是不同风险，因此可以同时报告。

## 为什么加入对抗性审查

两者没有职责冲突。Standard 关注结构和约定，对抗性审查关注代码在不可信环境下的实际表现。把它们分开，可以：

- 发现普通测试没有覆盖的安全和并发漏洞；
- 区分“代码不合规范”和“代码可能被利用”；
- 在质量门全绿时，仍检查资源耗尽、路径竞态等真实风险。

本项目的三轨审查应分别记录 `Standards`、`Spec` 和 `Adversarial` 的依据与证据。相同根因可以在不同轨道分别出现，但不能重复计数，也不能用对抗性意见冒充项目规范。
