# Issue Tracker 工作约定

## 目的与权威边界

本仓库使用 **GitHub Issues** 跟踪尚未关闭、需要执行的问题。

| 信息 | 权威来源 | 用途 |
|---|---|---|
| 未关闭问题的状态、优先级、负责人、阻塞关系、关闭条件 | GitHub Issue | 当前执行与协作 |
| 如何创建、关联、核销 Issue | 本文 | 统一工作流 |
| 每轮审查的基线、证据、复现结果和结论 | `docs/handoff/codex-handoff-*-*-code-review.md` | append-only 审计轨迹 |

本文不是问题清单，也不替代 GitHub Issue。Issue 关闭后，历史审查记录仍保留；Issue 是当前状态的唯一权威来源。

## 工具要求

代理必须优先使用 GitHub CLI `gh` 创建、查询、更新、评论和关闭 Issue，例如 `gh issue create`、`gh issue view`、`gh issue edit`、`gh issue close`。

- 不得以手工编写的 Issue 编号代替实际创建结果；
- `gh` 未安装、未认证、无仓库权限或命令失败时，必须明确报告阻塞原因；
- 未获得用户授权时，不得创建与当前任务无关的 Issue，也不得更改他人 Issue 的状态。

## 创建与关联

审查发现的问题按以下规则处理：

- P0、P1：必须创建或关联一个 GitHub Issue；
- P2：只要需要代码、文档或测试修改，或预计跨轮审查，必须创建或关联 Issue；
- P3：由审查者判断；若只是当轮建议且无需追踪，可只写入 handoff；
- 已有 Issue 时不得重复创建，应把新的证据、复现或范围追加到原 Issue。

Issue 至少包含：

```md
## 问题

一句话说明缺陷或缺口。

## 影响

受影响的行为、风险或阻塞阶段。

## 证据

- 审查轮次与 handoff 路径/标题
- 相关文件、提交或复现命令

## 关闭条件

- 必要的代码或文档变更
- 覆盖该问题的测试
- 复审验证命令及预期结果
```

标签遵循仓库已有约定：至少标记对应的 `phase-N`；阻塞后续阶段时使用 `phase-6-blocker`。只有在仓库已有对应标签时才添加额外分类标签。

## Handoff 的 append-only 规则

审查完成后，继续向对应的 `codex-handoff-*-*-code-review.md` 追加一小段轮次记录，但不复制 Issue 全文。每个未关闭项只写：

```md
- #123：P1，新增/仍未关闭；本轮证据：……
- #124：已关闭；修复提交：……；复测：……
```

规则：

1. 不修改旧轮次的发现或结论；
2. 新发现先创建/关联 Issue，再在 handoff 记录 Issue 编号和简短证据；
3. 修复后由下一轮复审决定是否关闭，不能仅凭修复提交自行标记关闭；
4. handoff 记录“当时为何这样判定”，Issue 记录“现在由谁处理、是否已关闭”。

## 关闭与阶段收口

关闭 Issue 前必须具备修复提交、相应测试以及后续复审的核销记录。阶段收口时，roadmap 只保留仍未关闭的 Issue 指针；ADR 只沉淀长期有效的决策，不复制 Issue 细节。
